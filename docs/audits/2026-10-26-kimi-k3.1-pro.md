# Audit

No files were modified. Unless otherwise noted, paths are relative to `files/config/custom/`. Kopia behavior was checked against its current documentation and source; no destructive tests were run against a live ApisCP or Wasabi installation.

## 1. Security

### Critical — Site-controlled symlinks escape restore destinations

**Location:** `kopia-backup/src/Runner.php:517-543`, `Runner.php:667-700`

Copy restores operate beneath the site admin’s writable home. A site owner can replace `~/restore`, or a predicted dated subdirectory, with a symlink to a host path. Root then calls `is_dir()`, `mkdir()`, Kopia, `chown()`, and `chgrp()` through that path.

The PHP ownership loop is directly exploitable: if `~/restore` points to `/etc`, `fileowner($root)` and `chown($root, ...)` follow the symlink and can change ownership of host `/etc`. Live restores similarly accept paths beneath the site-controlled `fst` tree. Kopia’s filesystem writer uses `os.Stat` and ordinary path-based opens, which follow directory symlinks; it does not confine writes to the original target ([upstream source](https://raw.githubusercontent.com/kopia/kopia/master/snapshot/restore/local_fs_output.go)).

**Trigger:** Plant the symlink, then have an admin perform a copy or live restore. Restored filenames are attacker-controlled through the site snapshot; `--delete-extra` increases the potential damage.

**Fix:** Restore first into a newly created root-only directory outside every site tree. Use `lstat()` on every path component and reject symlinks, but do not rely on pre-checks alone: use descriptor-relative operations with beneath/no-symlink resolution, such as `openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS)`, or a similarly confined helper. Never run `chown()` through a site-controlled pathname. Apply the same confinement to live restoration and deletion.

### High — CSRF validation still accepts a cookie without a form token

**Location:** `apps/kopiabackup/kopiabackup.php:76-98`

Requiring POST does not prevent CSRF when the session token supplied automatically in a cookie is accepted by itself. A cross-origin form cannot read the hidden token, but it can submit actions while the browser attaches cookies.

**Exploit:** Where cookies are sent with the request, an auto-submitting form can change settings, schedule jobs, reset state, or initiate an in-place restore. The attacker does not need to read the response.

**Fix:** Require a nonempty posted `Auth_UI::CSRF_KEY` and compare it with `Session::token()` using `hash_equals()`. Remove the cookie-only alternative. Keep SameSite session cookies as defense in depth, not as the primary check.

### High — Parallel first runs can generate different master secrets

**Location:** `kopia-backup/src/Kopiabackup_Module.php:745-756`, `Kopiabackup_Module.php:250-257`

Master creation is an unlocked get/generate/set sequence. The first `run_all` starts several independent `cpcmd` processes, so multiple children can observe no key and generate different masters.

**Trigger:** Run the first-ever backup with `parallel >= 2`. One process can create a repository using a master that another process subsequently overwrites in the keyring. That repository’s password is then lost, and future connections fail. `import_master()` has a similar check/set race.

**Fix:** Protect master creation and import with one host-wide exclusive lock. After acquiring it, re-read the keyring before generating or importing. Return the already-created value if another process won the race.

### Medium — Recovery instructions disclose the master through process arguments

**Location:** `README.md:531-532`, `kopia-backup/src/Kopiabackup_Module.php:725-737`

The documented rebuild command places the master directly in a shell command. It can persist in root’s shell history and appear in the process list while `cpcmd` runs.

**Trigger:** Follow the documented `cpcmd kopiabackup:import-master <master>` procedure on a multi-user host.

**Fix:** Add an interactive hidden prompt or read the secret from standard input/a root-only file. Do not accept it through the normal command-line invocation, and remove the inline secret from the generated recovery instructions and shell history examples.

### Medium — A stolen backup key can impose unbounded object-lock storage costs

**Location:** `apps/kopiabackup/kopiabackup.php:337-364`, `kopia-backup/src/BucketCheck.php:337-385`

The key necessarily receives `PutObject` and `PutObjectRetention`. Although the checks prevent it from shortening locks or permanently deleting versions, they do not prevent uploading large objects with very long locks or extending existing locks. Kopia explicitly identifies this ransomware cost-amplification risk ([Kopia documentation](https://kopia.io/docs/advanced/ransomware-protection/)).

**Exploit:** With the Wasabi key, upload data under the allowed prefix with long COMPLIANCE retention, or extend existing object retention.

**Fix:** Configure Wasabi bucket/account quotas, billing alerts, and abnormal-upload monitoring. If Wasabi supports suitable retention conditions or a separate maintenance credential, constrain retention changes without removing Kopia’s renewal capability.

### Low — Lock verification can miss defective older objects

**Location:** `kopia-backup/src/BucketCheck.php:57-120`

Only the newest 25 objects by default, plus `kopia.repository`, are checked. An unlocked, short-locked, or wrong-mode older pack can evade every weekly check while the report says locks were confirmed.

**Trigger:** Have a defective object outside the newest sample, for example from an older misconfigured repository or an isolated failed retention request.

**Fix:** Describe verification as sampled everywhere, including the final success message. For stronger assurance, use S3 Inventory or a persisted full-object inventory and audit every data object periodically.

## 2. Correctness and PHP

### High — Changing bucket, endpoint, region, or prefix does not reconnect existing sites

**Location:** `kopia-backup/src/Runner.php:189-225`

If `kopia.config` exists and `repository status` succeeds, `ensureRepo()` returns without comparing the active connection with current settings.

**Trigger:** Change only the prefix or bucket while the same credentials remain valid for the old repository. Backups continue writing to the old location even though the UI and lock verification use the new settings. This also defeats the README’s suggestion to change prefixes to abandon an old locked repository.

**Fix:** Store a fingerprint of endpoint, region, bucket, prefix, domain, and relevant repository identity. Reconnect whenever it differs. Verify the connected repository’s actual location after connecting.

### High — Snapshots with ignored file errors are reported as successful

**Location:** `kopia-backup/src/Runner.php:235-241`, `Runner.php:371-407`, `Runner.php:80-81`

The policy enables `--ignore-file-errors` and `--ignore-dir-errors`. `snapshot()` records each snapshot’s `numFailed`, but no code rejects a nonzero value. An empty or unexpected decoded result can also produce an empty snapshot report without failing the run.

**Trigger:** Files disappear, become unreadable, or encounter I/O errors during snapshot creation. Kopia can complete with skipped entries, after which the plugin sets `report.ok = true`.

**Fix:** Require valid JSON and expected snapshot IDs/sources. Treat any `numFailed > 0` or missing source as a failed/degraded backup, surface the paths in the report, and do not show an unqualified green status.

### High — Whole-site `--delete-extra` can remove ApisCP system-layer files

**Location:** `kopia-backup/src/Runner.php:371-380`, `Runner.php:517-531`

The snapshot contains `shadow`, but an empty-subpath live restore targets the composite `fst`. ApisCP’s `fst` also contains read-only template/system layers that are absent from `shadow` ([ApisCP filesystem documentation](https://docs.apiscp.com/admin/Filesystem/)).

**Trigger:** Select **Entire site**, **Back in place**, and **also remove files not in snapshot**. Kopia can classify lower-layer files as extra and delete/whiteout them from the site. Ignored live paths such as logs and temporary files are also eligible for deletion.

**Fix:** Disable `--delete-extra` for whole-`fst` restores. Restrict deletion to known data-only subtrees, preferably by operating on a safely confined `shadow` target with an explicit preservation policy.

### High — File restores are non-atomic and can hide permission failures

**Location:** `kopia-backup/src/Runner.php:527-540`

The restore does not enable `--write-files-atomically` or `--no-ignore-permission-errors`. Kopia defaults to truncating files in place and ignoring permission errors ([restore flags](https://kopia.io/docs/reference/command-line/common/restore/)). A successful process exit therefore does not prove a complete restore.

**Trigger:** A network failure, full disk, interrupted process, or permission error during an in-place restore. The live tree can contain a mixture of old, new, and truncated files while the plugin returns the restore path as success.

**Fix:** Enable atomic file writes and disallow ignored permission errors. For live restores, build and validate a confined staging tree, then switch directories atomically where possible. Preserve the previous tree until success and report any partial outcome explicitly.

### High — Live database replacement is neither complete nor transactional

**Location:** `kopia-backup/src/Runner.php:615-639`

Importing a dump over an existing database only drops/recreates objects represented in that dump. Tables created after the snapshot can survive. The import is not wrapped in a database-wide transaction, and applications remain live.

**Trigger:** Import into a live database with extra tables, active writes, or an import error. Failure leaves a partially restored database; success can leave a mixture of snapshot and post-snapshot objects. A failed “new” restore also leaves its newly created partial database behind.

**Fix:** Restore into an empty staging database and validate it. Quiesce application writes, back up the current database, then perform a controlled swap. Alternatively, explicitly empty the target before import, acknowledging that this still needs downtime and rollback. Remove failed staging databases.

### High — ACL restoration changes unrelated paths and failures still return success

**Location:** `kopia-backup/src/Runner.php:536-540`, `Runner.php:553-576`

Every live restore, including a single subdirectory, applies the run’s entire recursive `/var/www` ACL dump. It can therefore roll back permissions on files outside the requested restore path. Restore failure, missing ACL data, and `setfacl` failure are only logged.

**Trigger:** Restore one old subdirectory after changing ACLs elsewhere under `/var/www`, or restore when the ACL snapshot is missing/corrupt. Unrelated permissions change, or the requested files remain without required ACLs, while the restore reports success.

**Fix:** Filter the ACL dump to the exact restored subtree and reject entries outside it. Treat missing or failed ACL restoration as a failed/degraded restore unless the administrator explicitly overrides it.

### Medium — ACL dump failure can snapshot an empty or partial ACL file

**Location:** `kopia-backup/src/Runner.php:356-368`, `Runner.php:371-380`

`getfacl` writes directly to `acl.txt`; shell redirection truncates the previous good dump before the command runs. Failure only emits a warning, and the partial file is subsequently snapshotted.

**Trigger:** `getfacl` fails midway or cannot read part of the tree. The backup remains green and its later restore cannot reconstruct permissions reliably.

**Fix:** Write to a temporary file, require complete success, then rename atomically. Fail the backup or mark it explicitly unrestorable-with-ACLs; never silently replace the last good dump with a partial one.

### Medium — Reset and restore do not participate in the per-site lock

**Location:** `kopia-backup/src/Runner.php:48-58`, `Runner.php:500-547`, `kopia-backup/src/Kopiabackup_Module.php:181-200`

Only `Runner::run()` acquires the per-site lock. Verify and restore do not. `reset()` checks for a running backup, then deletes state without holding the lock, leaving a check/delete race and ignoring active restores.

**Trigger:** Reset while a restore/verify is active, or start a backup immediately after reset’s running check. Configuration, staging SQL, logs, and cache can disappear underneath another process. Restores can also overlap backups and produce inconsistent snapshots.

**Fix:** Use one per-site operation lock around backup, verify, restore, and reset. Make reset acquire it before rechecking and deleting; choose explicit shared/exclusive semantics if read-only overlap is desired.

### Medium — A transient connection error is treated as proof that no repository exists

**Location:** `kopia-backup/src/Runner.php:208-223`

Any failed `repository connect` is logged as “none found” and followed by `repository create`.

**Trigger:** Network outage, throttling, expired credentials, or endpoint failure while a repository already exists. Creation then fails against the existing prefix, obscuring the original error and prolonging the outage.

**Fix:** Distinguish Kopia’s authenticated “repository not found” result from transport, authorization, and parsing failures. Attempt creation only for a definitive absence; propagate all other errors.

### Medium — Existing repositories are verified against settings they do not use

**Location:** `kopia-backup/src/Runner.php:217-225`, `kopia-backup/src/Kopiabackup_Module.php:155-170`

Lock mode and period are set only during repository creation. Later edits are not applied to that repository, but `verify_locks()` expects every sampled object to match the newly configured mode and period.

**Trigger:** Change `lock_days` or `lock_mode` on an existing installation. Increasing days produces false failures; decreasing them validates against weaker protection than the repository actually has. Generated lifecycle advice also follows the new value rather than the repository’s actual lock period.

**Fix:** Read and persist each repository’s actual retention configuration and use it for verification/lifecycle calculations. Require an explicit migration or repository recreation to change it.

### Medium — `run_all()` has a return-type error on missing settings

**Location:** `kopia-backup/src/Kopiabackup_Module.php:241-249`

`run_all()` declares `: array` but returns `error()`, conventionally `false`, when settings are missing. Under strict return types this causes a `TypeError` instead of the intended error response.

**Trigger:** Run `run-all` before configuring all required fields, including through the UI when only a bucket has been entered.

**Fix:** Declare `array|bool`, consistently return an error result array, or throw and handle an exception. Add a CLI test for incomplete settings.

### Low — Restores cannot address runs beyond an arbitrary 1,000-group cap

**Location:** `kopia-backup/src/Runner.php:644-651`

`findRun()` searches only `listSnapshots(1000, false)`, although retention permits far more daily snapshots.

**Trigger:** Restore a retained run older than the newest 1,000 groups. The backend reports “no snapshot run” even though Kopia still retains it.

**Fix:** Look up the requested run tag directly, paginate until found, or make the limit cover configured retention rather than silently truncating.

## 3. Operational

### Medium — A two-day lock has almost no tolerance for missed maintenance

**Location:** `kopia-backup/src/Settings.php:230-236`, `kopia-backup/src/Runner.php:242-244`, `Runner.php:270-281`

The minimum lock is two days, full maintenance is every 24 hours, and verification is normally weekly. One disrupted full-maintenance window can put lock expiry before the next successful renewal; the two-day staleness check does not itself run daily.

**Trigger:** Set `lock_days=2`, then lose backup/maintenance execution for roughly two days.

**Fix:** Require a larger safety margin—at least several maintenance intervals—run maintenance health checks daily, and alert well before expiry. Consider a shorter full interval for small lock periods.

### Low — `keep_days < lock_days` is accepted despite creating long-lived orphan data

**Location:** `kopia-backup/src/Settings.php:108-111`

This combination only emits a warning. Maintenance can remove snapshot manifests after `keep_days`, while their blobs remain locked and billed for the much longer lock period.

**Trigger:** For example, set two-day snapshot retention and a 90-day lock. History disappears from normal Kopia listings after two days, but storage remains locked for months.

**Fix:** Reject this combination by default or require an explicit advanced override that explains point-in-time recovery and storage consequences.

### Medium — “Sample 25” verification lists and stores every object first

**Location:** `kopia-backup/src/BucketCheck.php:60-75`

Every page is fetched and appended to `$objects`, then the entire repository is sorted before sampling. At 1,000 sites this produces substantial LIST cost, runtime, and memory use, with up to eight sites doing it concurrently.

**Trigger:** Weekly verification of mature repositories containing large object counts.

**Fix:** Stream pages and use reservoir sampling, use S3 Inventory, or maintain a bounded object inventory. Fetch `kopia.repository` separately instead of retaining and sorting the full repository.

### Medium — Most log classes have no retention limit

**Location:** `kopia-backup/src/Runner.php:718-725`, `Runner.php:745-753`, `Runner.php:770-799`

Only plugin `run-*.log` files are pruned. Restore logs, verification logs, and Kopia’s own CLI logs are not covered. File and database restores started in the same second can also share one `restore-...log` filename.

**Trigger:** Repeated restores/verifications across 1,000 sites, or large Kopia error output over time.

**Fix:** Apply byte/count/age limits to all local log types, including Kopia logs; use unique names with microseconds or a random suffix and synchronize concurrent writers.

### Medium — One hung site can stall the entire nightly queue indefinitely

**Location:** `kopia-backup/src/Kopiabackup_Module.php:384-425`, `files/systemd/kopia-backup.service:6-10`

The pool has no per-child timeout or global deadline. A hung `cpcmd`/Kopia process leaves the loop waiting forever and prevents all pending sites from starting.

**Trigger:** An unresponsive filesystem, Kopia process, database dump, or network operation at any site—especially costly when 999 sites remain queued.

**Fix:** Add per-site timeouts, termination and failure reporting, a global nightly deadline, and independent retry scheduling. Monitor total queue duration rather than only individual backup results.

### Medium — Timer and manual “all sites” runs lack global exclusion

**Location:** `kopia-backup/src/Kopiabackup_Module.php:307-358`, `files/systemd/kopia-backup.service:8`

The timer starts `kopia-backup.service`; manual runs start the distinct transient `kopia-backup-run-all.service`. They can execute concurrently. Per-site locks then turn overlapping backups into immediate failures rather than waiting. Conversely, if the static service remains active past the next calendar event, that timer invocation is effectively missed.

**Trigger:** Start **Back up all sites** near 02:30, or have a nightly run last into the next day.

**Fix:** Add a global `run_all` lock shared by every invocation. Queue or skip manual runs cleanly, and alert when a nightly run approaches the next schedule.

### Medium — Status polling scales linearly with sites and open admin pages

**Location:** `kopia-backup/src/Kopiabackup_Module.php:479-522`, `apps/kopiabackup/kopiabackup.js:71-87`

Every poll constructs `SiteConfiguration` and reads several state files for every active site. Busy pages poll every ten seconds; multiple admin sessions duplicate the work.

**Trigger:** Approximately 1,000 sites, particularly while jobs are active or several admins have the page open.

**Fix:** Maintain an atomic aggregate status cache updated by workers, paginate the table, and poll only visible/changed state. Increase intervals substantially at large site counts.

### Medium — Local SQL and restore staging require unbounded root-filesystem space

**Location:** `kopia-backup/src/Runner.php:313-350`, `Runner.php:602-634`

Each site retains a full uncompressed SQL dump, temporarily creates another `.tmp` copy during export, and restores download another full dump. This is in addition to Kopia caches.

**Trigger:** Large databases or many sites can exhaust `/var/lib` or the root filesystem. A dump failure needs enough space for both old and new copies; a restore needs additional space again.

**Fix:** Document and enforce capacity headroom, check free space before dump/restore, meter cache growth, and alert on watermarks. Avoid claiming off-site backup removes the need for substantial local storage.

### Medium — Deleted or renamed sites leave repositories indefinitely

**Location:** `kopia-backup/src/Kopiabackup_Module.php:250`, `apps/kopiabackup/kopiabackup.php:367-376`

Only active sites are enumerated; there is no decommission flow. Once a site disappears, maintenance stops adding delete markers. Because lifecycle current-version expiration is intentionally forbidden, the orphaned repository’s current objects can remain forever.

**Trigger:** Delete an account, abandon a domain, or change storage prefixes after backups exist.

**Fix:** Add an explicit decommission operation that inventories and plain-deletes every repository key, creating delete markers so lifecycle can remove noncurrent versions after locks expire. Track and report orphaned prefixes.

## 4. Ansible and installation

### Medium — Blade lint does not validate Blade/PHP expressions

**Location:** `tasks/main.yml:58-65`

`php -l` sees `@php`, `@endphp`, `@if`, and `{{ ... }}` outside a real PHP opening tag as inline HTML. Consequently, linting `index.blade.php` does not parse the expressions or directive bodies.

**Trigger:** Introduce a syntax/type error in Blade PHP or a malformed expression. The pre-deployment lint still passes and failure is deferred to page rendering.

**Fix:** Compile templates with ApisCP’s Blade compiler in a disposable validation step, then lint the compiled PHP. Keep direct `php -l` for ordinary PHP files.

### Medium — Failed installed-hook lint leaves modified live files without rollback

**Location:** `tasks/main.yml:67-78`, `tasks/main.yml:111-138`

Plugin code and managed blocks are installed before the final lint of `boot.php` and `admin.php`. If that lint fails, the play stops with those changes still in place; there is no restoration of prior files.

**Trigger:** An invalid managed edit or a pre-existing customization that becomes syntactically invalid during installation/upgrade.

**Fix:** Build and lint candidate hook files before replacement, back up every touched file, and install atomically. Roll back code, hooks, and units on any validation failure.

### Low — Routine `upcp -b` can silently upgrade or downgrade Kopia

**Location:** `tasks/main.yml:22-33`, `tasks/main.yml:140-148`, `kopia-backup/src/Settings.php:23-24`

The default is `latest`, the add-in runs on every Bootstrapper installed stage, and downgrades are allowed. An otherwise unrelated panel update can therefore change the backup binary and repository-format behavior without a backup/restore compatibility gate.

**Trigger:** Run `upcp -b` after Kopia publishes a new release, or select an older exact version.

**Fix:** Default to a tested pinned version, make upgrades explicit, and run repository compatibility checks plus a test backup/restore before enabling the new binary across all sites.
